# 1. Product Requirements Document (PRD)

## 1.1 Product summary
Asrar-e-Tibb is a health-information and pharmacy community product with an existing Flutter Android app and Supabase-backed services. The work adds a more modern mobile UI, a responsive public website, a carefully scoped Rust API, and safer identity/data access. This document describes intended behavior; it is not evidence that each feature already exists.

## 1.2 Goals
- Make medicine discovery understandable, searchable and visually trustworthy.
- Let doctors/pharmacists share educational articles and allow community discussion without exposing private user data.
- Provide a credible pharmacy shopping experience with honest order/payment status.
- Provide private reminders and notes per account.
- Add a paid doctor/pharmacist consultation path when a real payment provider and provider verification are ready.
- Provide a responsive web interface on Vercel and a reliable APK download.
- Reduce authorization vulnerabilities, accidental data leaks and deployment risk.

## 1.3 Audiences and roles
| Role | Intended capabilities | Restrictions |
|---|---|---|
| Guest | Browse public medicine info and public articles; view product website; download the Android app | No private data, posting, private reminders, orders or consultations |
| Patient/general user | Manage own profile, posts if allowed, comments, likes, own reminders/notes, own cart/orders | Cannot read or edit another user's private data; cannot promote own role |
| Doctor | Public profile only after verification; publish health articles; participate in eligible consultations | Verification and professional credentials must be reviewed; not allowed to access patient data without an authorized consultation relationship |
| Pharmacist | Verified profile; educational posts; eligible paid consultations | No access to other users' records outside explicit workflow |
| Seller/shop owner | Manage only authorized listings/inventory if this workflow exists | Cannot change other sellers' products/orders or set trusted payment/order status |
| Admin/moderator | Manage users and content within role grants; review reports; suspend abusive accounts | All sensitive actions audited; no blanket browsing of private reminders/notes/health information |
| Super-admin | Manage admin assignments and system configuration through guarded process | No self-promotion by ordinary users; high-risk actions require audit and ideally re-auth/second approval |

## 1.4 Core modules
1. **Medicine directory:** search and filters for generic/brand, strength, form, manufacturer, class, indication and other fields only when the dataset actually provides them; medicine detail pages with mapped images.
2. **TibbNews:** educational posts/articles, author role/status, safe media, likes, comments, sharing via URL, reporting and moderation.
3. **Farmacia:** categories, catalog, product detail, cart, checkout, order status and availability based on trusted data. Do not describe checkout as “live” until its order/payment process has been tested.
4. **Reminders & notes:** private CRUD, schedule display and completion tracking; owner-only access.
5. **Prescription:** a route/page visibly marked “Coming soon.” Do not imply OCR or AI exists yet.
6. **Consultation:** doctor/pharmacist discovery and a pay-first workflow. Consultations remain locked unless server-side payment confirmation is valid. If payment integration is not configured, show an honest disabled/coming-soon state.
7. **Admin/moderation:** role-scoped moderation, account status, verification decisions, audit trail.
8. **Download page:** latest signed APK, version/build date, SHA-256, release notes, installation note and fallback to GitHub Releases.

## 1.5 Web sitemap
- `/` — home hero, medicine search, categories, selected dataset-backed products, community editorial highlights, service/trust strip, Android download.
- `/medicines` and `/medicines/[slug-or-id]` — searchable catalog and details.
- `/categories/[slug]` — category view based on real data.
- `/tibb-news` and `/tibb-news/[id]` — public feed/article details; interactions require sign-in.
- `/pharmacy/cart`, `/checkout`, `/orders` — state-aware storefront; private routes require authentication.
- `/consultation` and `/consultation/[providerId]` — show only verified providers; booking is locked until verified payment integration is ready.
- `/reminders`, `/notes`, `/profile`, `/settings` — private authenticated routes.
- `/prescription` — Coming soon.
- `/download` — verified APK release info.
- `/privacy`, `/terms`, `/medical-disclaimer`, `/contact` — real policy/legal copy reviewed by owner, not invented claims.
- `/admin` — protected administration, only if needed in web UI, not hidden behind CSS alone.

## 1.6 Non-functional requirements
- Mobile-first responsive layouts and keyboard accessibility; semantic HTML; WCAG-aware contrast and focus states.
- Stable deep links, graceful empty/loading/error states, useful network retry behavior.
- Private fields never appear in public API output, logs, analytics or client cache.
- RLS and least-privilege policies; automated cross-user authorization tests.
- Server-side configuration validation and sanitized logging.
- Performance: paginate feeds/catalogs, avoid downloading all image assets or the entire dataset at first render, use optimized responsive images, cache public data only when safe.
- Reliability: migrations are reversible or have documented recovery, backups precede schema changes, health/readiness checks, release rollback.

## 1.7 Scope boundaries
- Do not implement AI diagnosis/prescription extraction now.
- Do not invent medicine clinical guidance, inventory, prices, testimonials, verification or payment success.
- Do not make production payment collection available before provider selection, webhook verification, refunds/error handling and legal review.
- Do not replace Supabase entirely just to “have a backend.” Add Rust only where a trusted server adds measurable value.

## 1.8 Acceptance criteria
- The listed public/private routes render consistently on mobile, tablet and desktop.
- Medicine information comes from mapped existing assets/data; missing fields stay missing rather than fabricated.
- A logged-in user cannot retrieve another user's private reminders, notes, orders, private profile fields or uploads by changing IDs or API parameters.
- Client users cannot assign themselves doctor/pharmacist/seller/admin/verified/payment-paid states.
- Consultation access only unlocks based on verified server payment state.
- APK link points to a real signed release and has a verified checksum.
- Tests, environment settings, data policies and rollback instructions are documented.
