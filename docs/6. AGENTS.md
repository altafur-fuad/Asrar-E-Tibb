# 6. Agent Operating Rules (Antigravity / AI coding agents)

## Source of truth and order of work
1. Existing source code and verified database schema are the truth for current behavior.
2. `docs/` documents desired behavior, but do not assume the implementation matches it.
3. The owner explicitly approves production database, auth-provider, payment, permission, release signing and deployment changes.
4. Audit → plan → implement a small task → run tests → report files changed and evidence. Do not attempt a whole-project rewrite in one pass.

## Required before edits
- Read root README, `SETUP_COMPLETE_GUIDE.md`, `pubspec.yaml`, source tree, auth/service classes, datasets, platform config and all existing tests.
- Run `git status --short`; never discard or overwrite local user changes.
- Identify current build/test baseline and separate pre-existing failures from new failures.
- Map existing feature screens, navigation and services to each requirement.
- Export/inspect DB schema, RLS, grants, Storage policies and triggers if access exists. If not, mark them unverified instead of guessing.

## Code quality rules
- Prefer clear small modules, typed models, validated inputs, error states and testable service boundaries.
- Do not introduce unnecessary frameworks, duplicated auth stores, or a second database just because the desired backend language is Rust.
- Use dependency versions supported by the installed SDKs; explain major upgrades before applying.
- Never put secrets in client code, tracked files, generated source maps or logs.
- Do not disable RLS, lint, TLS verification, certificate checks or tests to make a build pass.
- Do not hide unfinished functionality behind fake success states. Use an honest disabled/Coming Soon state.
- Use existing medicine dataset/images as source of truth; no invented medical facts or product claims.
- Keep user-visible changes accessible and responsive. Do not clone the exact reference-site logos/wording.

## Database/security rules
- No `DROP`, `TRUNCATE`, destructive `ALTER`, broad grants, blanket policy, or production migration without explicit approval and recovery plan.
- Do not solve RLS failures by disabling RLS or moving all data into a service-role API.
- Test cross-user boundaries with two test users; test anon, authenticated, each domain role and admin separately.
- Role/verification/payment/order authority belongs to trusted server/database state, not browser form fields or `user_metadata` controlled by the user.
- Record all high-impact admin actions and protect audit logs from regular-user modification.

## Change reporting template
At the end of each milestone report:
1. Goal and scope completed.
2. Files added/modified with key reasoning.
3. Commands actually run and exact pass/fail results.
4. Security and migration impact.
5. Manual checks still required.
6. Environment/deployment variables the owner needs to configure (names only, never values).
7. Rollback instructions.
8. Next smallest milestone.

## Finish definition
Never say production-ready just because the homepage renders. Require security tests, RLS/Storage policy verification, web/mobile builds, tests, secrets scan, deployment health checks and a reviewed rollback path.
