# 5. API Contract (Proposed — verify before implementation)

The Rust API should be small and explicit. Existing Supabase queries may remain client-direct behind RLS. These endpoints are a design starting point, not proof that routes exist.

## 5.1 Conventions
- Prefix: `/api/v1`; health: `/healthz`, readiness: `/readyz`.
- JSON requests/responses; validate body, query and path fields; enforce body-size limits and request timeouts.
- Authenticated routes require a verified Supabase access token. Authorization is performed on the server and/or with user-scoped database permissions.
- Standard errors: `{ "error": { "code": "...", "message": "Safe user-facing message", "request_id": "..." } }`. Do not return stack traces or secrets.
- Use cursor/page pagination and bounded page sizes. Never return private profile fields from public endpoints.
- Do not accept client-supplied `role`, `is_admin`, `verified`, `owner_id`, `payment_status=paid`, order total or provider approval as trusted fields.

## 5.2 Candidate endpoint groups
| Endpoint | Auth | Purpose / invariant |
|---|---|---|
| `GET /healthz` | Public | Liveness only; no secrets/system internals |
| `GET /readyz` | Public/internal | Dependencies are ready; response is sanitized |
| `GET /api/v1/medicines` | Public if data intended public | Search/filter/paginate actual dataset-backed catalog |
| `GET /api/v1/medicines/{id}` | Public if intended | Return only mapped safe medicine fields |
| `GET /api/v1/feed` | Public for published posts | Paginated published posts only |
| `POST /api/v1/posts` | User | Optional server-mediated create; author comes from JWT subject |
| `POST /api/v1/orders` | User | Recalculate prices/availability on trusted side; create pending order, do not trust client total |
| `GET /api/v1/orders` | User | Only caller's orders unless tightly privileged staff workflow |
| `POST /api/v1/consultations` | User | Create booking/payment intent after provider and business-rule validation |
| `GET /api/v1/consultations/{id}` | Related parties only | Verify caller is patient/provider or authorized operator |
| `POST /api/v1/webhooks/{provider}` | Provider signature | Verify raw-body signature, timestamp, idempotency and state transition |
| `POST /api/v1/admin/moderation/actions` | Moderator/admin | Role-check + reason + immutable audit trail |

Do not implement an endpoint when equivalent safe direct access is simpler, or when the actual schema has not been audited. Avoid making a generic endpoint that lets callers name arbitrary tables/columns.

## 5.3 Authentication and authorization
- Extract bearer token; verify signature/issuer/audience/expiry using a maintained validation library and the issuer's documented key discovery process.
- Use `sub` as authenticated subject only after validation. Load trusted role/verification status server-side; never use unsigned client metadata as authorization.
- Check object-level permission for every ID in path/body. Use 404 vs 403 consistently to avoid resource enumeration where appropriate.
- Use per-route least privilege and deny by default. Do not pass a service-role key to the browser.

## 5.4 Orders and consultation payment
- Server recalculates totals using trusted catalog/stock data; client total is for display only.
- Use explicit states such as `pending_payment`, `paid`, `cancelled`, `failed`, `refunded` only after agreeing the actual domain model.
- Payment confirmation is accepted only from a verified provider webhook or trusted server-to-server verification. A client redirect/success screen is not proof of payment.
- Persist webhook event IDs and enforce uniqueness/idempotency. Reject replays/invalid signatures; verify amount, currency, order/booking reference and final state transition.
- Never expose consultation content/links/session access until server state is `paid` and the booking is valid. Define refunds, cancellation and chargeback behavior before launch.

## 5.5 Security and operational controls
- CORS allowlist contains explicit website origins; no wildcard plus credentialed requests.
- Rate-limit login-adjacent APIs, comments/posts, order creation and webhooks appropriately.
- Sanitize logs; include request IDs but never bearer tokens, secrets, payment payloads with sensitive data, or reminder/prescription content.
- Use timeouts, capped retries and bounded concurrency. Avoid logging complete SQL parameters when they may contain PII.
- Document OpenAPI or an equivalent request/response schema after routes stabilize; generate clients only after contract review.
