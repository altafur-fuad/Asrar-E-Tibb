# 8. Project Implementation Roadmap

## Phase 0 — local setup and baseline
- Get source on the owner’s Windows laptop; inspect Git status and backup user changes.
- Install/check Flutter, Dart, Git, Node LTS and Rust stable as needed; Docker Desktop only if local containers are needed.
- Run `flutter doctor`, `flutter pub get`, `flutter analyze`, `flutter test`; make a baseline report.
- Inventory screens, routes, services, datasets, image mappings, SQL files and build configs.
- Export current Supabase schema/policies and confirm backup/recovery access. No production writes in this phase.

**Gate:** audit report has real file paths, actual test results, and unverified items clearly called out.

## Phase 1 — data/security audit and highest-risk fixes
- Audit auth initialization, signup role assignment, admin checks, session refresh/logout, blocked user behavior, deep links and redirect URLs.
- Export and inspect every exposed table's grants/RLS, Storage policy, view/function/trigger; inspect public profile/private data separation.
- Write threat model and reproducible cross-user tests.
- Fix only reviewed high-risk issues with additive, tested changes. Prepare staging SQL migrations and rollback plan.

**Gate:** no production migration until owner approves and staging tests prove expected access and denial.

## Phase 2 — design system and Flutter polish
- Document current navigation and screenshot every key current screen if possible.
- Define shared colors, typography, spacing, component states and responsive constraints.
- Update one vertical slice at a time: app shell/navigation → medicine list/detail → TibbNews → Farmacia/cart → reminder/notepad → profile/admin.
- Test on Android across small and large layouts. Preserve feature parity and local dataset loading.

**Gate:** core app routes remain usable and analyzer/tests have no unreported new regression.

## Phase 3 — separate Vercel website
- Initialize Next.js/TypeScript in `website/`; do not overwrite Flutter `web/`.
- Implement header, search-first homepage, medicine catalog/detail from real data, TibbNews public reading, account flow, cart/order routes as supported, private pages and APK download.
- Reuse the design tokens from `docs/2. DESIGN.md`; use reference screenshots for structure, not exact copy.
- Connect Supabase client with public-safe env variables and tested policies. No service role or secret key in client bundle.
- Add mobile/keyboard/accessibility tests and production build.

**Gate:** website build passes, routes and auth redirects work with staging Supabase, cross-user access tests pass.

## Phase 4 — Rust API / business workflows
- Build Axum app only for selected server-owned workflows. Define OpenAPI/schema; validate JWTs; add request IDs, timeouts, CORS allowlist, rate limit and health checks.
- Add idempotent order/consultation/payment state transitions and signed webhook verification only after choosing a real payment provider.
- Docker build, unit/integration tests, migration compatibility, secret scanning and Render readiness checks.

**Gate:** no fake paid state, replay/fraud tests pass, Docker image builds, server configuration validated.

## Phase 5 — APK, release and staged deployments
- Build a release APK using the project’s actual Android application ID and signing config. Do not generate/commit or expose signing key material through chat.
- Attach signed APK, checksum and release notes to a GitHub Release. Verify downloaded artifact hash.
- Deploy website preview to Vercel and API to Render staging; set Supabase redirect/origin allowlists, CORS and environment variables.
- Run acceptance, privacy, accessibility, smoke and rollback tests; owner signs off before production.

## Phase 6 — post-launch
- Configure error/uptime monitoring with PII scrubbed, backups/retention, update/release policy and dependency/security scanning.
- Review feedback and error logs without exposing health data.
- Roll out paid consultations only after identity verification, payment provider, refund/chargeback state, provider availability, consent/privacy and support flow are all ready.

## Definition of done
A phase is done only when acceptance criteria in its gate have been demonstrated and documented. No green checkmark for tasks not actually run.
