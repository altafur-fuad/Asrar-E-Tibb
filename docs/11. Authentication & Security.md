# 11. Authentication, Authorization & Security Checklist

This document is a threat-model checklist, not a statement that current code is secure. Complete it against actual Dart, SQL, Storage rules, Next.js code and Rust handlers.

## 11.1 Security objectives
- A user only accesses data and actions allowed for their identity, role, relationship and current resource state.
- The browser/mobile app is untrusted. It may be modified; every authorization decision must be enforced by Postgres RLS or a trusted server.
- Admin privileges are narrow, explicit, logged and revocable.
- Secrets and health/personal data stay out of public bundles/logs.

## 11.2 Auth lifecycle audit
- [ ] Supabase is initialized once with the correct project URL and client-safe publishable/anon key.
- [ ] No `service_role`, secret key, database password, webhook secret or payment secret is present in Dart, Next.js public env, static assets, source maps, Git history or client logs.
- [ ] Sign-up cannot choose `admin`, `super_admin`, `verified`, `blocked=false` or trusted profession status.
- [ ] Email verification/reset/OTP flows have safe error messages, throttling and exact redirect allowlists.
- [ ] Session persists/refreshed via supported SDK behavior; logout clears local/private caches and subscriptions.
- [ ] Blocked/deactivated accounts are rejected server-side and RLS/endpoint policies enforce this consistently, not only by hiding UI.
- [ ] Admin creation/promotion requires an owner-controlled, audited procedure with re-auth and ideally a second admin approval for sensitive changes.
- [ ] App deep links/website redirects cannot be redirected to arbitrary attacker-controlled domains.
- [ ] Account deletion/export/data retention and orphaned Storage data behavior are defined.

## 11.3 Role and verification policy
Suggested roles: `patient` (or regular user), `doctor`, `pharmacist`, `seller`, `moderator`, `admin`, `super_admin`. Use only roles the actual product needs. Role assignment must be stored in a protected source of truth; client-editable `user_metadata`, local preferences or request JSON cannot grant authority. Prefer professional verification as a separate approval state with verifier, timestamp and audit evidence. A verified doctor badge is not the same as an authenticated account.

Role permissions should be matrix-driven. Example: doctors can publish articles after approval; a patient can read approved public articles; moderators can remove reported public content; sellers can manage only their own approved inventory if seller management is actually enabled. Admins should not automatically receive access to personal notes, reminders, prescription files or private consultation content. If exceptional support access is essential, require purpose, time-bounded access and immutable audit logging.

## 11.4 Data classification and access
| Data | Default access |
|---|---|
| Public medicine catalog fields | Public read only if intended; writes by import/admin path |
| Published public posts/articles | Public or signed-in read per product decision; author edits own; moderators moderate |
| Draft/unpublished posts | Author and expressly authorized reviewers only |
| Public profile fields | Selected fields only |
| Email, auth IDs, private profile data | Owner and narrowly authorized account workflow |
| Reminders and personal notes | Owner only by default |
| Orders and payment details | Owner and minimum staff workflow; never other customers |
| Prescription uploads / private health records | Owner and specifically authorized clinical workflow; not ordinary admin browse |
| Consultation records/messages | Related patient/provider within valid paid booking; audited exceptions only |
| Role assignments, verification state, block status | Trusted role-management workflow only |
| Security audit log | Write-only from application flow where possible; read to authorized security/admin role; not mutable by ordinary users |

## 11.5 Supabase/Postgres controls
- [ ] RLS enabled on every table exposed through API or client roles.
- [ ] Grants checked alongside RLS; no accidental broad `anon` permissions.
- [ ] SELECT/INSERT/UPDATE/DELETE policies individually reviewed.
- [ ] UPDATE uses both row visibility and correct `WITH CHECK` for resulting row.
- [ ] `user_id`/owner/author columns cannot be overwritten to seize another user's row.
- [ ] Views, RPCs, triggers and `SECURITY DEFINER` functions reviewed for bypass paths and safe `search_path`.
- [ ] Public profile projection does not leak private columns.
- [ ] Admin role is checked from trusted DB state or trusted JWT claims under documented minting rules; no user-controlled claim.
- [ ] SQL tests/`supabase test db` or equivalent are configured where possible.
- [ ] Storage buckets have explicit read and upload/update/delete policies; folder paths are not the only check unless bound to authenticated owner. MIME type and file size validated.
- [ ] Realtime subscriptions are tested for unauthorized cross-user row events.

## 11.6 Rust API controls
- [ ] Validate JWT signature, issuer, audience, expiry and subject with maintained code/library.
- [ ] Derive trusted roles/approvals from server-side source; never accept role or owner from client.
- [ ] Validate object-level authorization on every resource ID and state transition.
- [ ] Use request-size limits, timeouts, CORS allowlist, rate limiting and safe errors.
- [ ] Service-role key (if unavoidable) stored only in Render secret settings and never logged. Remember that a service role bypasses RLS; server endpoints then require explicit authorization and tests.
- [ ] Webhook signature verification uses the provider's official method and raw request body as required.
- [ ] Webhook event idempotency, amount/currency/reference checks, and valid state-transition logic are tested.
- [ ] No open proxy, generic SQL endpoint, arbitrary file fetch or unsafe URL redirect.
- [ ] `/healthz`/`/readyz` do not reveal credentials, full env, stack traces or internal topology.

## 11.7 Website/mobile controls
- [ ] All private routes validate current session and server/database permissions; client-side redirects are UX only.
- [ ] Query caches clear on logout/account switch; private data is not shared between user sessions.
- [ ] User HTML/Markdown/URLs are sanitized/validated; links use safe schemes; images validate MIME/size.
- [ ] No local storage of long-term secrets beyond SDK-managed session design; do not log access tokens.
- [ ] Avoid caching private API responses in public CDN caches or static generation.
- [ ] Verify source maps and build output don't include env secrets.

## 11.8 Required adversarial tests
1. User A tries to read/update/delete User B's reminder, note, order, profile-private field, upload and consultation: all denied.
2. Anonymous guest attempts protected writes: denied.
3. User edits request JSON/local storage to set `role=admin`, `verified=true`, `owner_id=B`, `payment_status=paid`: ignored or denied.
4. Unverified doctor/pharmacist tries to post as verified provider or access consultations: denied.
5. Seller tries to edit another seller's inventory/order: denied.
6. Admin moderation works, but routine private notes/reminders remain unreadable unless explicit policy is approved.
7. Storage path traversal, wrong owner path, oversized file and fake MIME type are rejected.
8. Expired/forged/wrong-issuer JWTs fail; logout and blocked-account requests fail.
9. Duplicate/replayed/invalid payment webhooks cannot double-unlock or double-charge.
10. Realtime subscriptions, views and RPCs do not bypass row permissions.

## 11.9 Incident response
Document how to revoke sessions/keys, disable an abused API, rotate leaked keys, roll back deployment, restore backup, preserve audit evidence and notify affected users where required. Do not paste credentials or private database exports into AI prompts.
