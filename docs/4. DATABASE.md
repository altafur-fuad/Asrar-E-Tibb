# 4. Database & Data Integrity Plan

## 4.1 Do not guess the current schema
The public project README names several entities such as users, posts, likes, comments, notifications, medicines and Supabase Storage buckets. These names are not proof of exact SQL types, constraints, indexes, ownership or deployed state. Export the actual schema, RLS policies, grants, triggers, functions and Storage policies first. Record differences between local SQL and production. Do not run speculative `DROP`, `TRUNCATE`, table recreation or broad permission SQL in production.

## 4.2 Schema audit inventory
For every table/view/function/storage bucket record:
- name and purpose; whether it contains public, private, health, payment or moderation data;
- primary key, foreign keys, uniqueness, nullability, check constraints and indexes;
- created/updated timestamps and trigger logic;
- grants for `anon`, `authenticated`, service/admin roles;
- RLS enabled state and every SELECT/INSERT/UPDATE/DELETE policy;
- ownership column and whether it can be modified by a client;
- views/security-definer functions and whether they can bypass intended checks;
- consumers in Flutter/web/backend; row counts only when safe; backup and migration strategy.

## 4.3 Logical domains to map to existing tables
Use these as design concepts, not table names to create blindly:
- Identity: Supabase `auth.users` identity reference, public profile, protected role assignments, professional verification status.
- Medicines: canonical medicine item, generic/brand relationships, manufacturer, dosage form, strength, indications/description, source/import metadata, image mapping.
- Community: posts/articles, post media, likes, comments/replies, reports, moderation action/audit records, notifications.
- Personal: medication reminders, reminder event/completion history, personal notes. Owner-scoped by authenticated subject.
- Commerce: cart/session, order, order item snapshot, fulfillment/delivery status, payment attempt/event ledger, refund state if relevant.
- Consultation: provider profile/verification, booking, payment state, session access grant, cancellation/refund state and audit events.
- Future prescription: placeholder route now; schema/upload/OCR should be separately designed after consent, retention, access and security requirements are agreed.

## 4.4 Data modeling rules
- Use UUIDs or existing stable IDs consistently; do not change primary keys without migration mapping.
- Store money as integer minor units (e.g., paisa) plus currency, not floating point. For Bangladesh, do not assume currency/payment provider in code if deployment config may differ; owner must confirm.
- Use UTC timestamptz internally and render locale/timezone in clients.
- Add foreign keys, unique constraints for deduplicated actions (e.g. one like per user/post), check constraints for valid status transitions and indexes for actual query patterns.
- Order items must preserve purchase-time product name/strength/price snapshot so catalogue edits do not rewrite historical orders.
- Track import batch/source and row-level issues for medicine datasets; preserve the original file and do not silently discard unknown columns.
- Keep public profile fields separate from sensitive/private fields where RLS is easier to reason about.
- Role and verification state are trusted administrative data. Do not allow clients to update them.
- Use soft delete only when product/audit requirements justify it; clearly define data retention and eventual purge.

## 4.5 RLS and grants checklist
- Every exposed table has RLS enabled and reviewed.
- Grants are least-privilege. Policies do not revoke SQL grants automatically.
- `anon` sees only intentionally public rows (e.g. published medicine info and public articles).
- `authenticated` users see/edit only their own private rows; public interactions are limited to permitted operations.
- For UPDATE policies, validate both old-row visibility and new-row constraints (`USING` and `WITH CHECK` where needed).
- Do not allow changing `user_id`, `owner_id`, `author_id`, order total, payment state, moderation role or verified state through a client update.
- Likes have uniqueness and ownership checks; comments require allowed parent objects; posts require valid author identity and status.
- Audit `SECURITY DEFINER` functions, views, triggers and RPCs with the same care as tables.
- Review Storage RLS/object policies for `post-images`, `profile-pictures` and any new buckets; restrict upload size/type and per-user paths; signed URLs should be short-lived when content is private.
- Test using real separate user accounts and the anonymous role. A query from a database-owner connection is not proof that RLS works.

## 4.6 Migration workflow
1. Export and safely store schema/policy definitions; take or verify a recoverable backup.
2. Map current columns to proposed domain model.
3. Write versioned, additive migration files and a rollback/recovery note.
4. Run migrations and policy tests in local/staging first; seed only synthetic data.
5. Test old-app compatibility during rollout; consider expand → migrate/backfill → switch reads/writes → contract.
6. Owner approves production migration, window, backup and rollback plan.
7. Record migration version and results. Never run unreviewed SQL in production from an AI-generated answer.

## 4.7 Medicine data images
Discover actual JSON/CSV assets and image directories before designing import. Produce a field dictionary and deterministic relation between medicine IDs/slugs and local image paths. Report missing/duplicate images. A local dataset can be the source of public directory seed data, but the commerce inventory/price/stock must have a distinct trusted source; do not assume medical dataset records are sellable stock.
