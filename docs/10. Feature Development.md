# 10. Feature Development Guide

## 10.1 Work in vertical slices
For each feature, implement the screen, data contract, permission, loading/error states, tests and documentation together. Before starting, find the existing implementation and define what “done” means.

## 10.2 Medicine directory
- Inventory current JSON/CSV files and models; document columns and image paths.
- Define canonical display fields supported by real data; avoid showing fake dosage/side-effect/disease-treatment claims.
- Search/filter by fields that exist; debounce requests; paginate/virtualize; use image placeholders for missing images.
- Verify product images against medicine IDs or validated local filename mapping. Never infer that a nearby file is the correct medicine photo.
- Add tests for malformed JSON/CSV, duplicate IDs, Unicode/Bangla text, absent image, long generic names and case-insensitive search.

## 10.3 TibbNews
- Define permitted authorship roles and what verification means.
- User identity and author ID come from auth context/server, not submitted fields.
- A user can edit/delete only their own post/comment, unless a moderator role has an explicit moderation grant.
- Prevent duplicate likes with database uniqueness and atomic upsert/delete behavior.
- Use pagination and safe rich-text rendering; cap post/comment/media sizes.
- Add user reporting, moderation history and rate limits if absent.

## 10.4 Farmacia and orders
- Separate medicine-information records from sellable product/stock/price data unless the current data model legitimately joins them.
- Cart is a convenience layer; server/database recalculates final totals, availability, discounts, tax/delivery and currency from trusted config at checkout.
- Persist line-item snapshots. Prevent order ID guessing, changing item prices, modifying other users' orders or making an order paid from the client.
- If payment is not integrated, label checkout as demo/unavailable and do not accept real money.
- Seller workflows require tenant/owner scoping, approval and product moderation.

## 10.5 Reminders and notes
- All records are private to their owner unless an explicit sharing feature is designed and consented to.
- Use timezone-aware schedules, clear reminder permissions, safe notification behavior and deletion/export rules.
- Do not log note/reminder text. Avoid exposing reminder titles through analytics or server error messages.
- Add cross-user tests for list/detail/update/delete and guessable IDs.

## 10.6 Paid doctor/pharmacist consultation
1. Display provider only if verified and available.
2. User chooses provider/time and receives a server-created booking/payment intent.
3. Payment provider checkout runs; redirect alone does not unlock service.
4. Webhook verifies signature, event ID, amount/currency, reference and valid transition.
5. Server sets paid state atomically and unlocks access only to the correct patient/provider pair.
6. Handle pending, failed, cancelled, refunded, duplicate and chargeback states.
7. Log business event metadata only; keep sensitive consultation content out of logs.

Before selecting a provider, design an interface/adaptor and keep the live payment option disabled. Provider choice, merchant onboarding, refunds, fees and Bangladesh-specific compliance need owner confirmation.

## 10.7 Prescription “Coming soon”
- Create accessible informational page and navigation slot only.
- Do not accept files or imply AI detection exists.
- Before implementing, define file retention/deletion, consent, MIME/size controls, access roles, OCR accuracy, human review, audit trail and health-data privacy.

## 10.8 UI quality bar
Every component covers loading, no results, error, retry, unauthenticated, permission denied and long-content states as relevant. Use semantic HTML/accessible controls on web and touch-friendly controls on mobile. Use the reference screenshots for visual hierarchy, not copied brand names or claims.
