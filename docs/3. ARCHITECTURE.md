# 3. Architecture & System Boundaries

## 3.1 Proposed architecture
```text
Android (existing Flutter app)          Responsive Website (Next.js/TypeScript)
       |                                               |
       | Supabase client + user JWT                    | Supabase client + user JWT
       | public/publishable key only                    | public/publishable key only
       v                                               v
+-------------------------- Supabase -------------------------------+
| Auth (identity/session) | Postgres + RLS | Storage policies | Realtime |
+-------------------------------------------------------------------+
                               ^
                               | validated Supabase JWT / trusted server operations
                      Rust API (Axum) on Render + Docker
                      - order/consultation invariants
                      - trusted payment webhooks
                      - privileged, audited operations
                      - rate limits / integration adapters
```

This is a target diagram, not a verified description of current code. First map existing clients/services and determine whether a Rust API is necessary for every workflow. Do not proxy every simple read through Rust without a security/performance reason.

## 3.3 Authentication responsibility
- Supabase Auth is the identity provider and source of user sessions.
- Clients may hold only public/publishable keys and the current user's short-lived session tokens using supported SDK/session handling.
- RLS protects direct client reads/writes to Postgres; grants and policies both matter.
- Rust API validates Supabase access tokens using official JWT/JWKS guidance or a trusted supported library and validates audience/issuer/expiry/signature. Never trust an ID/role in JSON without comparing it with the authenticated subject and trusted records.
- Choose one authorization source-of-truth. Avoid duplicating role state in client preferences, user-editable profile metadata and independent backend tables that drift.

## 3.4 Rust API scope
Good initial use cases:
- Creating a consultation/order state transition under server-side rules.
- Creating payment checkout sessions with a real provider.
- Receiving/validating payment webhooks and preventing duplicate processing.
- High-risk admin tasks with audit records.
- Third-party integrations that require server secrets.
- Notification dispatch or scheduled server tasks if needed.

Usually keep direct Supabase reads with RLS for public medicine records, own profile fields, own reminders/notes and feed interactions if policies provide sufficient protection. The final split must be based on audit findings.

## 3.5 Deployment boundaries
- Vercel hosts only the website project in `website/`. Configure correct root directory/build command. Keep private variables out of browser bundles.
- Render hosts `backend/` as a Docker web service. The Rust process binds to `0.0.0.0:$PORT`; expose `/healthz` and preferably `/readyz`.
- Supabase hosts Auth/Postgres/Storage/Realtime. Use its dashboard for config and reviewed migrations; do not include database credentials in `website`.
- GitHub Releases stores signed APK artifacts; the website points to a verified release URL. Website hosting is not a substitute for Android signing/release management.

## 3.6 Reliability and observability
- Structured request logs with request ID, status, latency and route; avoid body/token/health-data logging.
- Error monitoring must scrub email, access tokens, private article data, reminder content and uploaded filenames when sensitive.
- Add timeouts and bounded payload sizes; pagination for listing APIs.
- Health checks should report service health without disclosing internal configuration or secrets.
- CI: format/lint/test/build for affected projects, secret scanning, dependency audit and migration/policy tests.

## 3.7 Architecture decision records
Create a short ADR before each substantial choice (web framework, JWT verification strategy, role source, payment provider, data migration, storage strategy). Each ADR states context, options, decision, security/cost implications and reversal plan.
